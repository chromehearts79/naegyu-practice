# 내규가 바뀌었을 때: 내규챗봇 유지보수 안내

처음이면 먼저 `docs/담당자_시작_안내.md` 를 한 번 따라 합니다. GitHub 화면은 영어라서, 눌러야 할 영어 버튼 이름을 그대로 적었습니다.

## 한 장 요약

```
① 알림 메일  →  ② Claude 웹에서 고치기  →  ③ 합치기 버튼  →  ④ 새 판 받기  →  ⑤ 망연계로 배포
 (자동)          ("내규 개정 반영")        (Merge pull request)   (자동으로 만들어짐)   (사람)
```

챗봇의 답은 미리 써 둔 **문답 카드**에서 나옵니다. 내규가 바뀌면 바뀐 조문을 근거로 쓴 카드만 골라 고칩니다. 골라내기는 프로그램이, 고쳐 쓰기는 Claude 가 하고, 사람은 읽어 보고 합치기 버튼을 누릅니다. **Claude 는 합치지 않습니다.**

## 이럴 때 이렇게

| 상황 | 할 일 |
|---|---|
| 알림 글(이슈)이 왔다 | 아래 "알림 글의 종류와 할 일" |
| 내규관리부서가 개정 파일을 먼저 줬다 (ALIO 에 아직 없다) | 아래 "ALIO 보다 먼저 받은 파일 올리기" |
| 새 내규가 생겼다 | 알림 글(새 내규)이 오거나, 파일을 위처럼 올린 뒤 Claude 에게 "새 내규 추가"라고 말한다. 파일 이름은 `Ⅳ-30. ○○지침.hwp` (코드는 내규분류표 위치) |
| 내규가 폐지됐다 | Claude 에게 폐지된 내규를 알려 준다. 관련 카드를 정리해 준다 |
| 계산기가 틀린 금액을 냈다는 신고 | 아래 "계산기 신고" |

## 개정 반영하는 법

1. `claude.ai/code` 에서 `naegyu-chatbot` 저장소를 열고 **"내규 개정 반영"** 이라고 말합니다. 알림 글이 있으면 그 번호도 말해 주면 좋습니다. 중간에 끊겼으면 **"개정 반영 이어서"** 라고 말합니다.
2. Claude 가 단계마다 결과를 쉬운 말로 알려 주고 다음에 할 말을 알려 줍니다. 그대로 따라 말합니다.

| 단계 | 일어나는 일 |
|---|---|
| 0 준비 | 프로그램을 쓸 수 있게 준비 (자동) |
| 1 파일 받기 | 매주 확인이 받아 둔 파일(`대기/`)을 `원본/` 의 맞는 이름으로 옮김. 새 내규면 분류 코드를 물음 |
| 2 변환·비교 | 바뀐 조문, 다시 확인할 카드·계산기, 양식(별지) 변화, 카드에 아직 안 담긴 바뀐 곳(새로 붙은 항 등)을 정리 |
| 3 카드 고치기 | 바뀐 조문에 맞춰 카드를 고치고, 다른 AI 가 조문만 보고 값을 다시 찾아 맞는지 확인 |
| 4 새 판 준비 | 판 번호를 올리고 화면을 다시 만들고 시험. 고치기 전과 후의 검색 시험 결과도 비교 |
| 5 올리기 | 바뀐 내용을 정리한 **Pull Request**(합쳐 달라는 요청서)를 엶 |

- 4단계 끝에 `ALIO 기록 갱신 실패` 라는 경고가 나와도 **정상**입니다. Claude 웹에서는 ALIO 에 접속할 수 없어서입니다. 합친 뒤 GitHub 가 알아서 다시 합니다.
- Pull Request 를 Claude 가 못 열면 요청서 글을 대화에 써 줍니다. Claude 웹의 `Create PR` 버튼, 또는 GitHub 의 `Compare & pull request` 버튼을 누르고 그 글을 붙여 넣습니다.

## 합치기 (사람이 하는 일)

1. GitHub 의 `Pull requests` 탭에서 그 요청서를 엽니다.
2. 글을 읽습니다. 카드마다 "무엇이 바뀌었나"가 한 줄씩 있습니다. 담당부서에 확인이 필요하다고 적힌 점은 따로 챙깁니다. "검색 시험 전·후"에 **새로 틀림**이 0개가 아니면 합치기 전에 Claude 에게 까닭을 물어봅니다.
3. 아래쪽에 **All checks have passed** (초록색)가 있는지 봅니다.
4. 맞으면 초록 `Merge pull request` → `Confirm merge`. 합치는 순간 챗봇이 바뀌는 것은 아니고, 몇 분 뒤 새 판 파일이 만들어집니다.

**합치면 안 되는 경우:** 시험이 빨간색(`Some checks were not successful`)이고 요청서에 "시험에 실패했습니다. 이 글을 합치지 말고 Claude 웹에 이 글을 보여 주세요"라는 댓글이 달렸을 때. 합치지 말고 그 댓글을 복사해 `claude.ai/code` 에서 Claude 에게 보여 줍니다. 까닭은 요청서의 `Checks` 에서 빨간 단계를 열면 보입니다. `판 번호 검사` 단계가 빨간색이면 판 번호가 오르지 않은 것입니다(다른 요청서가 먼저 합쳐졌거나 새 판 준비 단계를 건너뜀). 그 단계의 글을 Claude 에게 보여 주면 고쳐 줍니다.

## 새 판 받기와 망연계 (합친 뒤)

몇 분 뒤 시험을 다시 돌리고, 통과하면 새 판이 만들어집니다. 저장소 화면 오른쪽 `Releases` 에서 `내규챗봇 제N판` 을 엽니다.

- 받는 곳(Assets)에는 한글 이름표가 붙어 있지만, **내려받은 파일 이름은 영어**입니다. GitHub 이 한글 파일 이름을 깨뜨려서 올리기 때문입니다.

| 내려받은 파일 | 무엇인가 | 어디로 |
|---|---|---|
| `naegyu-chatbot-vN.html` | **직원에게 보일 챗봇.** 한 파일이면 끝 | **망연계로 내부망에 옮겨 올림.** 이 파일만 옮깁니다 |
| `naegyu-chatbot-vN-artifact.html` | claude.ai 게시용 | 필요할 때만 |
| `gpts-vN.zip` | 인터넷망 GPTs 용 지식 묶음 | 인터넷망 GPTs 를 쓰는 경우 |
| `review-workbooks-vN.zip` | 소관부서 검수표 | 바뀐 카드가 있는 소관부서에 보냄 |
| `changes-vN.md` | 바뀐 내용 요약 | 공지·기록용 |

- 옛 판은 내리고 새 판 파일로 바꿉니다. 직원 화면 맨 위에 "제N판"이 보이는지 확인합니다.
- 새 판이 안 만들어졌으면 아래 "새 판 실패"를 봅니다.

## 알림 글의 종류와 할 일

저장소 `Issues` 탭에 글이 생기고 메일이 옵니다. 제목의 앞부분이 종류입니다. 글에는 무엇이 달라졌는지, 바뀐 조문, 파일을 받아 둔 위치, 다음에 할 일이 적혀 있습니다.

| 제목 | 뜻 | 할 일 |
|---|---|---|
| 개정 의심: ○○ | ALIO 파일이 우리 판과 다르다 | 비교 결과를 보고 "내규 개정 반영". 반영할 게 없으면 `확인함` |
| 조문 밖 변화: ○○ | 조문은 같은데 별지 등 다른 글자가 달라졌다 | 달라진 글자를 보고 반영하거나 `확인함` |
| 담당자 확인: ○○ | 컴퓨터가 어느 파일이 현행인지 가릴 수 없었다 (까닭이 적혀 있다) | 받은 파일을 직접 보고 반영하거나 `확인함` |
| 새 내규: ○○ | 우리 판에 없는 내규가 ALIO 에 있다 | 넣을 것이면 "새 내규 추가", 아니면 `확인함` |
| 목록에서 사라짐: ○○ | 우리 판에는 있는데 ALIO 목록에 없다. 폐지라고 단정하지는 않는다 | 폐지됐는지 알아보고, 유효하면 `확인함` |
| 확인 실패: ALIO 매주 확인 | 접속 문제 등으로 확인하지 못했다. **"변동 없음"이 아니라 "알 수 없음"** | 다음 주 확인이 성공하면 **저절로 닫힘**. 몇 주 계속되면 Claude 에게 "확인 실패 이슈를 봐 줘" |
| 새 판 실패: 새 판 만들기 | 합쳤는데 새 판이 안 만들어졌다. 챗봇은 이전 판 그대로 | 아래 "새 판 실패" |
| 공개 점검 실패 | 직접 올린 파일 중에 올리면 안 되는 이름의 파일이 있을 수 있다 | **바로 정보보안담당관과 저장소 관리자에게 알립니다.** 처리가 끝나면 직접 닫습니다(`Close issue`). 저절로 닫히지 않습니다 |
| 매주 확인 기록 | 고정된 글. 매주 월요일 댓글이 달린다 | 읽기만 한다 |

- **확인함:** 파일을 반영하지 않기로 했거나 이미 반영해서 알림만 끝내고 싶을 때. 그 알림 글에 `확인함: 사유` 라고 댓글을 달고(`Comment` 버튼) 보냅니다. 예: `확인함: 같은 내용을 다시 올린 것` (`확인함 사유` 처럼 쌍점 없이 써도 됩니다.) 사유 없이 `확인함` 만 쓰면 사유를 적어 달라는 답이 옵니다. 내규 알림이 아닌 글에 쓰면 "알림 글이 아니다"라는 답이 옵니다. 쓰기 권한이 있는 사람만 됩니다. 판 번호는 오르지 않고, 알림 글은 닫힙니다. ALIO 값이 나중에 또 바뀌면 처음부터 다시 판정합니다.
- **개정 의심 등이 해결되면** 알림 글은 저절로 닫힙니다(새 판을 합치면 다음 확인 때).
- **14일이 넘으면** 글과 댓글에 `정 담당 확인, 부재면 게시판에 미반영 공지` 가 적힙니다. 정 담당이 확인하고, 자리에 없으면 게시판에 "ALIO 에 올라온 ○○ 개정이 아직 챗봇에 반영되지 않았다"는 **미반영 공지**를 올립니다.
- **알림 글은 사람 이름 없이** 내규 이름만 씁니다. 공개 저장소라서 누구나 볼 수 있습니다.

### 새 판 실패

`새 판 실패: 새 판 만들기` 글이 오거나, 매주 확인 때 "제N판이 아직 만들어지지 않았습니다"가 나오면:
1. GitHub 위쪽 `Actions` 탭 → 왼쪽에서 `새 판 만들기` → 오른쪽 `Run workflow` 버튼 → 초록 `Run workflow`. 다시 돌려 봅니다.
2. 또 실패하면 `Actions` 에서 빨간 실행을 열어 실패한 단계 이름을 Claude 웹에 보여 주고 "새 판 실패 이슈를 봐 줘"라고 말합니다.
3. 새 판이 만들어지면 그 이슈는 저절로 닫힙니다. 직접 닫을 필요가 없습니다.

## ALIO 보다 먼저 받은 파일 올리기

**먼저 읽어 주세요.** 이 저장소는 **공개**입니다. 올리는 순간 누구나 볼 수 있습니다.
- 시행문, 이름이 `[` 로 시작하는 파일(`[개정근거]` 등), 파일 이름에 직원 이름이 든 파일은 **절대 올리지 않습니다.**
- 올린 뒤에 지워도 기록(History)에는 남습니다. 혹시 올렸다면 바로 **정보보안담당관과 저장소 관리자에게 알려 주세요.** 자동 점검(`공개 점검 실패` 글을 만드는 검사)은 파일 이름만 보고, `[` 로 시작하는 이름과 연락처 파일만 잡습니다. 파일 안은 보지 못하므로, 일반 이름의 시행문이나 직원 이름이 든 파일은 잡히지 않아 올리는 사람이 올리기 전에 직접 확인해야 합니다.
- **ALIO 에 아직 올라오지 않은 내규는 정보보안담당관이 답하기 전에는 이 방법으로 올리지 않습니다.** 그때까지는 ALIO 에 올라오기를 기다리고, 자동 알림(`새 내규`, `개정 의심`)을 받아 진행합니다.

내규관리부서가 개정 파일을 ALIO 에 올라오기 전에 주었더라도, 정보보안담당관의 답을 받은 뒤에만 아래 방법으로 올립니다.

1. 내 PC에 폴더 `대기` 를 만들고, 그 안에 폴더 `<내규명>_직접` 을 만듭니다. 예: `대기\복무세칙_직접`. 받은 파일을 그 안에 넣습니다. 파일 이름은 `Ⅲ-3-1. 복무세칙.hwp` 처럼 `코드. 규정명.확장자` 로 맞춥니다.
2. 저장소 첫 화면에서 `Add file` → `Upload files` 를 누릅니다.
3. PC의 `대기` 폴더를 화면에 끌어다 놓습니다(폴더째 끌어야 폴더 이름이 그대로 올라갑니다).
4. `Commit directly to the main branch` 가 선택된 채로 `Commit changes` 를 누릅니다.
5. `claude.ai/code` 에서 "내규 개정 반영, 대기에 직접 올린 파일 있어"라고 말합니다.

이렇게 올려도 새 판은 시작되지 않습니다(새 판 만들기는 `대기/` 의 변화를 무시합니다). 챗봇에는 개정을 합치기 전까지 아무 변화가 없습니다.

**폴더 이름 끝이 반드시 `_직접` 이어야 합니다.** `<내규명>_숫자` 모양은 매주 확인이 받아 둔 폴더라서, 매주 확인이 다시 받아 덮어쓰거나 정리할 수 있습니다.

## 메일이 안 올 때

월요일 오전에 `매주 확인 기록` 글에 댓글이 하나도 달리지 않으면(메일도 없으면) 확인이 멈춘 것입니다.
1. 저장소의 `Actions` 탭 → `ALIO 매주 확인` 에 이번 주 실행이 있는지 봅니다. 빨간색이면 `확인 실패` 글이 있는지 봅니다.
2. 실행이 없으면 `Run workflow` 로 손으로 돌려 봅니다.
3. 그래도 안 되면 Claude 웹에 "매주 확인이 멈췄어"라고 말합니다.
- 예약 실행은 몇 분에서 한 시간쯤 늦게 시작할 수 있습니다. 저장소에 60일 동안 아무 활동이 없으면 GitHub 이 예약 실행을 끕니다. 매주 확인이 활동 기록을 남겨서 보통은 해당되지 않습니다.
- 알림 지정(메일이 가는 사람)은 저장소 `Settings` → `Secrets and variables` → `Actions` → `Variables` 탭의 `NAEGYU_ASSIGNEES` 입니다. GitHub 아이디를 적고, 두 사람이면 쉼표로 나눕니다. 바꾸려면 연필 아이콘 → `Update variable`.

## 그동안 화면은 어떻게 보이나

- 개정본이 반영됐는데 아직 카드를 다 고치지 않은 상태로 화면을 만들면, 바뀐 조문을 근거로 쓴 답에 **"규정 개정 · 재검수 전"** 표시가 붙습니다. 직원이 옛 기준으로 오해하지 않게 하는 안전장치입니다.
- 계산기 숫자의 근거 조문이 바뀌었는데 아직 고치지 않았으면 그 계산기는 "계산하지 않습니다"로 멈춥니다.
- 화면을 만든 지 90일이 지나면 위쪽에 "최신판인지 확인하세요" 안내가 뜹니다.
- 개정된 내규의 양식(별지)은 새 원본에서 다시 떼기 전까지 받기에서 빠집니다.

## 양식(별지) 받기

직원은 조문 아래나 내규나침반 맨 위 **'양식'** 칸에서 별지를 한글 파일로 받습니다. 어떤 별지가 있고 어느 조문이 부르는지는 서식 대장(`knowledge/forms.json`)에 있습니다. 조문이 부르는 이름과 별지 제목이 다르면(원문 번호가 틀렸을 수 있음) 그 조문에는 양식 칸을 달지 않습니다. 이때는 내규관리부서에 원문 확인을 부탁합니다. 양식 관련 변경은 Claude 가 2·3단계에서 정리해 줍니다.

## 계산기 신고

계산기가 틀린 금액·기간을 냈다는 신고가 **1건이라도** 들어오면 그 계산기를 바로 끕니다.
1. Claude 에게 "출장 여비 계산기 꺼줘"라고 말합니다. Claude 가 설정을 고치고 Pull Request 를 엽니다.
2. 확인하고 합치면 새 판이 만들어집니다. 그 계산기는 "점검 중"으로 바뀌고, 답과 근거 조문은 그대로 보입니다.
3. 원인을 고치고 담당부서 확인을 받은 뒤 같은 방법으로 다시 켭니다.

## 사용 시간과 한도

Claude 에는 사용 한도가 있어, 카드가 많은 개정은 중간에 멈출 수 있습니다. 그때는 시간이 지난 뒤 **"개정 반영 이어서"** 라고 말하면 열려 있던 작업을 찾아 이어 갑니다. 고친 카드는 자주 저장되므로 처음부터 다시 하지 않습니다.

개정 1건에 드는 시간과 한도는 **첫 실제 개정을 해 본 뒤 여기에 숫자를 적습니다.** (비어 있음)

## 모르고 넘어가기 쉬운 것

- AI 재확인은 "카드의 답을 모르는 AI 가 조문만 보고 값을 다시 찾는" 방식입니다. 카드 파일을 읽지 말라고 지시문으로 정했을 뿐 기술적으로 막지는 못합니다. 그래서 결과가 '확인 필요'로 나온 항목은 사람이 원문과 대조합니다.
- AI 가 만든 카드는 소관부서 검수 전까지 화면에 "AI 작성 · 담당부서 검수 전"으로 표시됩니다.
- 비공개 정보와 개인정보는 Claude 에게 입력하지 않습니다(인공지능전환관리세칙 제29조제2항). 개정 파일은 ALIO 에 공개되는 내규만 올립니다.

## 누가 무엇을

| 역할 | 할 일 | 시점 |
|---|---|---|
| 내규관리부서 | 개정·신설 내규 파일을 담당자에게 전달 | 개정 공포 때 |
| 담당자 | 알림 확인, "내규 개정 반영", 합치기, 새 판 받아 배포 | 시행일 전후 14일 안 |
| 소관부서 | 바뀐 카드 검수표 확인 | 배포 후 |

담당자가 바뀌면 이 안내서, `README.md`, `CLAUDE.md`, `knowledge/AUTHORING.md` 를 넘깁니다.

## 문제가 생기면

| 메시지 | 뜻과 할 일 |
|---|---|
| 같은 코드 파일이 2개 | 개정 전 파일이 `원본/` 에 남아 있음. Claude 에게 정리를 부탁 |
| 이름이 '코드. 규정명' 형식이 아님 | 파일 이름을 `Ⅳ-30. ○○지침.hwp` 처럼 바꾼다 |
| 카드 검사 오류 N건 | 조문 번호가 바뀌거나 삭제돼 인용이 깨진 카드. 3단계에서 Claude 가 고친다 |
| 변환 실패 | 한글 파일이 암호·DRM 으로 잠겨 있을 수 있음. 잠금 없는 파일로 다시 받는다 |
| `[계산기 …] 원문에 "…" 가 없음` | 계산기 숫자의 근거 문구가 개정으로 바뀜. Claude 가 계산기 숫자와 근거를 고친다 |
| 준비 중 "저장된 지문과 다른 조문" | 개정 작업 중이면 정상. 작업이 없는데 나오면 멈추고 Claude 에게 보여 준다 |

## 인계 할 일

사람이 바뀌거나 기관이 이 방식을 정식으로 쓰기 전에 확인할 것입니다.

**준비**
- [ ] 정 담당·부 담당 GitHub 아이디로 저장소 초대(쓰기 권한), `NAEGYU_ASSIGNEES` 입력
- [ ] 담당자 Claude 계정(Pro)과 GitHub 연결. 계정·저장소 소유를 개인이 아닌 기관 명의로 옮길지 정하기
- [ ] 외부망에서 `github.com`, `claude.ai/code` 접속과 알림 메일 수신 확인(회사 메일이면 스팸함)
- [ ] 인계 시험에서 확인: 위 "ALIO 보다 먼저 받은 파일 올리기"의 클릭 순서(`Add file` → `Upload files`, 폴더째 끌어놓기). 실제 화면에서 해 본 적이 없음
- [ ] 담당자가 `담당자_시작_안내.md` 의 연습을 끝까지 해 보기. 개정 3건 정도를 함께 해 보며 인계

**정보보안·기관 문서 (아직 제출 여부를 모르는 문서는 고치지 않았음)**
- [ ] 정보보안담당관 확인: ALIO 공시 전에 받은 원본을 외부 AI(Claude)에 입력해도 되는지, 내규를 공개 저장소에 두어도 되는지, 정보보안지침 제38조②(민간 클라우드 사용 조건)에 맞는지
- [ ] `reports/governance` 의 문서를 제출할 때 고칠 곳:
  - 운영 환경: "맥 1대, 고사양 PC" → GitHub(공개 저장소, Actions)와 Claude 웹(클라우드)
  - 독립 재확인: "로컬 AI 모델(고사양 PC 1대)" → Claude 하위 작업(또는 새 Claude 웹 세션)
  - 외부 AI 입력 정보와 보관 위치: 내규 원본과 문답이 공개 저장소와 Claude 클라우드에 있다는 점
  - 오류 신고 창구·담당자·개정 반영 절차(알림 → 반영 → 합치기 → 새 판)
  - 시범본을 claude.ai 에 비공개로 게시한 것을 계속 둘지

**이 방식으로 아직 안 된 일**
- 두 망 배포 자동화(인터넷망 게시, 망연계 절차 정리)와 인터넷망 보완 요청 받는 길
- 기관 PC에서의 실제 확인(메일, 접속)과, 비개발자가 이 안내만 보고 따라갈 수 있는지
